# AGENTS.md

## 1. 文件定位

本文件定义 AI 编程代理在本仓库中的工作方式与行为边界，适用于：

- Codex
- Claude Code
- Cursor
- 其他具备代码生成、代码修改、命令执行能力的 AI Agent

本文件面向的项目类型：

- Java
- Spring Boot
- 微服务
- DDD
- 企业级团队协作

本文件回答的问题是：

- AI 应该怎样理解需求
- AI 应该怎样阅读代码
- AI 应该怎样改代码
- AI 改完后必须做什么验证
- AI 在什么情况下必须保守处理

## 2. 规则优先级

当多份规则同时存在时，优先级如下：

1. 用户当前明确指令
2. 本文件 `AGENTS.md`
3. `./docs/code-rules.md`
4. `./docs/engineering-rules.md`
5. 仓库内模块级说明文档
6. 工具默认行为

若规则冲突，按高优先级覆盖低优先级执行。

## 3. AI Agent 的角色定义

AI Agent 在本仓库中不是“代码补全工具”，而是“企业研发协作代理”。

AI 必须做到：

- 先理解上下文，再动手修改
- 优先保证业务正确性、兼容性、可维护性
- 严守 DDD 分层与微服务边界
- 给出完整可审查的改动，而不是半成品
- 能补测试时补测试，能验证时做验证
- 如存在风险、假设、未验证项，必须明确说明

AI 禁止做的事：

- 未经说明直接引入破坏性变更
- 偷改外部接口、事件结构、数据库字段语义
- 把业务逻辑塞进 Controller、Mapper、SQL、RPC DTO
- 为了“看起来更优雅”做大面积无关重构
- 虚构测试通过结果、运行结果、压测结果
- 绕过安全、权限、审计、日志、监控要求

## 4. 默认工作流程

对于任何非 trivial 的任务，AI 必须按以下流程工作：

1. 识别当前需求影响的业务域、限界上下文、服务、模块、分层
2. 阅读相关代码、配置、测试、文档，禁止脱离上下文直接生成
3. 判断该变更影响的是：
   - 接口契约
   - 应用服务编排
   - 领域模型
   - 持久化
   - 消息/事件
   - 安全/权限
   - 可观测性
   - 配置或部署
4. 优先采用最小闭环改动完成目标
5. 补齐对应层级的自动化测试
6. 执行可执行的验证命令
7. 输出变更说明、验证结果、假设与风险

## 5. 修改前必须完成的分析

在正式编辑代码前，AI 必须尽量回答以下问题：

- 当前能力属于哪个限界上下文
- 当前代码位于哪一层：entry、application、domain、infrastructure
- 是否已有现成模式可复用
- 本次修改是否影响对外 API、RPC、事件、表结构、缓存键、幂等逻辑
- 是否会破坏既有兼容性
- 是否涉及跨服务、跨事务、跨上下文协作

如果上述问题不能明确回答，AI 必须：

- 采用保守方案
- 避免扩大变更面
- 在最终说明里显式写出假设

## 6. DDD 分层执行规则

### 6.1 Domain 层

领域层承载：

- Aggregate
- Entity
- Value Object
- Domain Service
- Domain Event
- Repository 接口
- 业务不变量

AI 必须遵守：

- 核心业务规则放在领域对象或领域服务中
- 领域对象不能依赖 Controller、HTTP、RPC DTO、ORM Entity
- 不变量必须在领域层保障，不能只靠前端或接口校验
- 有业务语义的标识、金额、地址、状态应优先抽成值对象

禁止：

- 在领域层直接写 SQL
- 在领域对象中依赖 Spring MVC、MyBatis、JPA Controller DTO
- 把状态流转规则散落在多个 service if/else 中

### 6.2 Application 层

应用层负责：

- 用例编排
- 事务边界
- 权限/策略协调
- 聚合装载与保存
- 事件发布协调

AI 必须遵守：

- 应用服务是用例入口，不是业务规则垃圾桶
- 一个 public 方法应表达一个明确用例
- 应用层不直接暴露底层持久化细节
- 应用层可以组合多个领域对象，但不应承载核心业务不变量

### 6.3 Entry 层

入口层包括：

- REST Controller
- RPC Provider / Facade
- MQ Consumer
- Scheduler 任务入口

AI 必须遵守：

- 入口层保持薄
- 边界校验在入口层完成
- Request DTO 转 Command / Query
- 不把接口 DTO 直接传入领域层
- 不直接返回数据库实体对象

### 6.4 Infrastructure 层

基础设施层包括：

- Repository 实现
- ORM / DO / PO
- 外部服务 Client
- MQ Producer
- Cache
- 分布式锁
- 文件存储

AI 必须遵守：

- 基础设施依赖业务抽象，不反向污染领域层
- 外部系统异常需要明确转换与记录
- 集成调用要考虑重试、超时、熔断、幂等、可观测性

## 7. 微服务边界规则

AI 必须把微服务边界视为强约束。

强制要求：

- 不允许直接读写其他服务数据库
- 不允许复用其他服务内部领域模型
- 服务间协作通过 API、RPC、事件、消息完成
- 默认保持向后兼容
- 默认优先增量演进，而不是直接替换

若改动影响其他服务，AI 必须明确说明：

- 影响的契约是什么
- 哪些调用方会受影响
- 是否需要版本化或迁移方案

## 8. 契约与兼容性规则

除非用户明确要求，否则 AI 不得随意破坏以下兼容性：

- HTTP API 字段
- RPC 方法签名
- 事件字段结构
- 错误码语义
- 幂等语义
- 数据库读写兼容性
- 缓存键语义

若不可避免需要破坏性修改，AI 必须：

1. 明确指出“这是破坏性变更”
2. 说明影响面
3. 给出版本演进或迁移方案

## 9. 数据库与持久化规则

AI 修改数据库相关逻辑时必须保守。

强制要求：

- 不得随意删除字段、改字段语义、改枚举含义
- 优先采用向后兼容的 Schema 演进方式
- Schema 变更、代码变更、数据回填顺序必须可说明
- 需要考虑默认值、空值、索引、历史数据兼容、回滚能力
- Repository 负责聚合持久化，不承载核心业务规则

推荐演进顺序：

1. 先加兼容字段或兼容结构
2. 再发布兼容代码
3. 再回填历史数据
4. 再切换读写逻辑
5. 最后清理旧结构

## 10. 消息、事件、异步任务规则

只要涉及 MQ、事件、异步消费、延迟任务，AI 必须显式检查：

- 幂等
- 重复消费
- 顺序性假设
- 重试安全
- 死信处理
- 补偿能力
- trace 和日志可追踪性

默认要求：

- 事件名表达业务事实
- 消息体字段明确、可演进
- 消费逻辑可重复执行而不破坏一致性

## 11. 安全与合规规则

AI 不能为“开发方便”降低安全标准。

强制要求：

- 在边界做输入校验
- 保留认证、鉴权、审计链路
- 日志中不得输出密码、token、密钥、敏感个人信息
- 不硬编码账号、密钥、地址、租户信息
- 权限上下文缺失时优先安全失败

禁止：

- 偷开 debug 接口
- 跳过权限校验
- 用固定测试密钥写入正式代码

## 12. 可观测性规则

凡是会影响生产行为的改动，AI 都必须考虑可观测性。

至少要检查：

- 失败时是否有可定位日志
- 是否带业务标识、traceId、请求标识
- 外部调用是否可追踪
- 关键业务动作是否可度量
- 日志是否泄露敏感信息

如果仓库已存在统一日志、埋点、Tracing 标准，必须复用，不得另起一套。

## 13. 测试规则

AI 必须按改动风险补测试。

最低要求：

- 领域规则修改：补单元测试
- 应用编排修改：补应用服务测试
- 接口行为修改：补接口测试或契约测试
- 持久化逻辑修改：补仓储或集成测试
- Bug 修复：尽量补回归测试

如果环境限制无法补测试，必须在结果说明中明确写出原因。

## 14. 变更范围控制

AI 必须以“最小闭环交付”为原则。

允许：

- 为完成需求进行必要的小范围抽取和整理
- 为提升可读性抽私有方法
- 与现有风格保持一致的小范围整理

默认不允许：

- 大面积重命名
- 横跨多个模块的无关重构
- 风格化批量格式调整
- 引入新框架替代旧框架
- 没有业务收益的大规模“架构优化”

## 15. 最终输出模板

AI 完成任务后，输出说明至少应包含：

- 修改了哪些文件
- 改了什么行为
- 为什么这样改
- 做了哪些验证
- 有哪些假设
- 还剩哪些风险或未验证项

推荐输出格式：

```text
变更摘要：
- ...

验证情况：
- ...

假设与风险：
- ...
```

## 16. 面向企业 Java 微服务项目的默认目录认知

AI 在没有更具体约束时，默认按如下目录认知项目：

```text
src/main/java/com/company/{domain}
  |- entry
  |  |- rest
  |  |- rpc
  |  |- mq
  |  |- scheduler
  |  |- assembler
  |
  |- application
  |  |- service
  |  |- command
  |  |- query
  |  |- dto
  |  |- assembler
  |
  |- domain
  |  |- model
  |  |- service
  |  |- event
  |  |- repository
  |  |- factory
  |  |- valueobject
  |
  |- infrastructure
     |- persistence
     |- rpc
     |- mq
     |- cache
     |- client
     |- config
```

若实际项目已有成熟结构，AI 必须优先遵循现有结构，不得强推模板。

## 17. AI 对外说明模板

如果用户要求“做一个新功能”，AI 应按如下方式理解与落地：

1. 先定位该功能属于哪个领域
2. 再确定入口层、应用层、领域层、基础设施层分别改什么
3. 先找现有模式
4. 只补完成该功能所需的最小代码
5. 补关键测试
6. 说明兼容性、风险、验证结论

## 18. 与其他规范文件的关系

AI 在本仓库工作时，必须同时遵守：

- `./docs/code-rules.md`
- `./docs/engineering-rules.md`

职责分工如下：

- `AGENTS.md`：约束 AI 怎么工作
- `docs/code-rules.md`：约束代码怎么写
- `docs/engineering-rules.md`：约束团队怎么交付
