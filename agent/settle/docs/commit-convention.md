# Commit 规范

## 1. 目标

Commit 规范的目标不是“好看”，而是：

- 便于 review
- 便于回溯
- 便于发布记录整理
- 便于排查问题时快速定位变更意图

## 2. 基本规则

- 一个 commit 只表达一个明确意图
- 不要把无关改动混在一起
- commit message 要说明“为什么改”
- 大变更要拆成多个可 review commit

## 3. 推荐前缀

- `feat:` 新功能
- `fix:` 缺陷修复
- `refactor:` 重构，不改变外部行为
- `test:` 测试相关
- `docs:` 文档相关
- `chore:` 杂项、构建、配置、脚本

## 4. 推荐格式

```text
<type>: <简短中文说明>
```

例如：

```text
feat: 支持交易订单幂等创建
fix: 修复支付回调重复消费导致状态错乱
refactor: 提取订单取消领域策略
test: 补充订单状态流转回归测试
docs: 更新 PR 模板与工程规范
```

## 5. 带需求单编号的格式

如果团队要求关联需求单或缺陷单，推荐：

```text
<type>: [<ticket>] <简短中文说明>
```

例如：

```text
feat: [OMS-1024] 支持订单创建接口幂等
fix: [PAY-2048] 修复支付回调重复入账问题
```

## 6. 不推荐示例

不推荐：

```text
update code
fix bug
修改一下
继续优化
大改
final
```

问题在于：

- 看不出范围
- 看不出意图
- 无法支持后续排查和发布说明

## 7. 拆分建议

一个较大的需求，建议拆成多个 commit：

1. `feat:` 增加领域能力
2. `feat:` 增加接口接入
3. `test:` 补齐回归测试
4. `docs:` 更新文档和发布说明

## 8. AI 提交补充要求

如果 commit 由 AI 协助生成，仍需满足：

- message 可读
- 与实际改动一致
- 不夸大验证结果
- 不把多个无关主题混在同一个 commit
