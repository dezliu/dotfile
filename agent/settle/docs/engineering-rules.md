# engineering-rules.md

## 1. 文件定位

本文件定义企业级 Java 微服务 / DDD 项目的工程交付规范。

本文件不关注“某一行代码怎么写”，而关注：

- 分支怎么管理
- 提交怎么写
- PR 怎么提
- 测试怎么分层
- CI/CD 怎么设门禁
- 数据库变更怎么上线
- 生产风险怎么控制

适用对象：

- 开发工程师
- 测试工程师
- 架构师
- Tech Lead
- DevOps / 平台工程师
- AI 编程代理

## 2. 工程原则

- 业务连续性优先于局部代码美感
- 小步快跑优先于大爆炸式重构
- 可观测、可回滚、可审计是工程质量的一部分
- 兼容性不是附加项，而是默认责任
- 团队统一约定优先于个人习惯

## 3. 分支管理规范

### 3.1 基本要求

- 使用短生命周期分支
- 一个分支只承载一个主题
- 禁止在一个分支里混入无关修改
- 分支名必须可追踪

推荐分支命名：

- `feature/order-create`
- `feature/refund-approve`
- `bugfix/payment-callback-repeat`
- `refactor/pricing-policy`
- `hotfix/order-status-fix`

如果团队使用需求单或缺陷单编号，推荐带编号：

- `feature/OMS-1024-order-create`
- `bugfix/PAY-2048-callback-idempotent`

## 4. Commit 规范

### 4.1 基本要求

- 一个 commit 表达一个清晰意图
- commit 要可 review、可回溯
- commit message 说明“为什么”，不是只说“改了什么”

### 4.2 推荐前缀

- `feat:`
- `fix:`
- `refactor:`
- `test:`
- `docs:`
- `chore:`

### 4.3 示例

```text
feat: 支持交易订单幂等创建
fix: 修复支付回调重复消费导致状态错乱
refactor: 提取订单取消领域策略
test: 补充订单状态流转回归测试
```

## 5. Pull Request 规范

每个 PR 必须包含以下内容：

- 业务背景
- 变更范围
- 是否影响接口/事件/数据库
- 风险点
- 验证方式
- 回滚或兜底方案

推荐 PR 模板：

```text
## 背景
- 为什么要做这次变更

## 变更内容
- 修改了哪些模块
- 新增/调整了什么行为

## 影响评估
- 是否影响 API：是/否
- 是否影响 RPC：是/否
- 是否影响 MQ/Event：是/否
- 是否影响 DB Schema：是/否
- 是否存在破坏性变更：是/否

## 风险与回滚
- 主要风险
- 回滚方式

## 验证记录
- 单测：
- 集成测试：
- 联调：
- 其他：
```

## 6. 代码评审规范

代码评审必须优先关注生产风险，而不是风格细节。

评审优先级如下：

1. 业务正确性
2. 数据一致性
3. 对外契约兼容性
4. 安全与权限
5. 可观测性
6. 测试充分性
7. 可维护性
8. 风格一致性

评审时必须重点检查：

- 是否破坏 DDD 分层
- 是否把业务逻辑写进 Controller / Mapper / Consumer
- 是否改坏外部契约
- 是否遗漏幂等、重试、超时、补偿
- 是否缺失关键测试
- 是否有日志但没有上下文

## 7. DoD 定义

一个需求或缺陷只有满足以下条件才算完成：

- 功能代码完成
- 相关测试完成
- 兼容性已评估
- 风险已评估
- 日志、监控、追踪需求已评估
- 配置变更已整理
- 数据库变更有上线顺序
- 代码评审意见已处理

## 8. 测试策略

### 8.1 测试分层要求

每次改动都应至少思考以下测试层：

- 单元测试
- 集成测试
- 接口/契约测试
- 端到端关键链路测试
- 回归测试

### 8.2 不同改动的最低测试要求

- Bug 修复：尽量补回归测试
- 新领域规则：必须补单元测试
- 接口改动：验证序列化、反序列化、错误码、兼容性
- 持久化改动：验证 repository 或集成行为
- MQ / 事件改动：验证幂等、重试、重复消费场景

### 8.3 测试稳定性要求

- 测试必须可重复执行
- 不依赖脆弱的共享环境
- 不制造随机失败
- 时间、顺序、时区敏感逻辑要显式控制

## 9. CI/CD 门禁规范

每个服务至少应具备以下流水线能力：

- 编译
- 自动化测试
- 静态检查
- 打包

推荐流水线阶段：

1. 依赖拉取与编译
2. 单元测试
3. 集成测试
4. 契约测试
5. 静态扫描与安全扫描
6. 制品打包
7. 部署与环境准入

禁止：

- 依赖“某个同学本地手动操作”的上线流程
- 没有测试结果就直接进生产
- 流水线失败但口头放行

## 10. 发布与上线规范

### 10.1 基本要求

- 优先小版本、频繁发布
- 高风险改动要灰度、分批、可回滚
- 发布必须可追踪到分支、commit、PR

### 10.2 高风险变更识别

以下变更默认视为高风险：

- 数据库 Schema 变更
- 外部接口契约变更
- 状态机逻辑变更
- MQ/事件结构变更
- 幂等、锁、事务逻辑变更
- 核心链路性能优化

### 10.3 高风险发布最少要有

- 开关或灰度策略
- 监控观察项
- 回滚条件
- 回滚步骤

## 11. 兼容性治理规范

兼容性默认是强要求。

合并前必须评估是否影响：

- API 调用方
- RPC 调用方
- 事件消费者
- 定时任务
- 数据库读写
- 报表和监控
- 前端页面

如需破坏兼容，必须提供：

- 版本策略
- 迁移路径
- 通知对象
- 下线节奏

## 12. 数据库变更规范

### 12.1 基本原则

- Schema 变更必须可 review
- 优先增量演进，不做一步到位破坏性修改
- 上线顺序必须考虑旧代码与新代码并存

### 12.2 推荐上线顺序

1. 先发布兼容 Schema
2. 再发布兼容代码
3. 再做数据回填
4. 再切换读写逻辑
5. 最后删除废弃结构

### 12.3 必查项

- 默认值
- nullability
- 索引影响
- 历史数据兼容
- 大表锁表风险
- 回滚后是否还能读写

## 13. 接口与契约治理

对外接口、RPC、事件 Schema 都属于“受治理资产”。

强制要求：

- 必须有 owner
- 契约变更必须和实现一起修改
- 优先增量演进
- 字段命名清晰稳定

如果仓库中存在以下文件，则它们属于事实标准：

- OpenAPI
- Swagger 定义
- protobuf
- Avro / JSON Schema

代码变更时必须同步更新这些定义文件。

## 14. 可观测性与运维规范

关键业务链路必须做到“出问题后可以定位”。

至少应具备：

- 结构化日志
- traceId / requestId 关联
- 错误指标
- 延迟指标
- 关键业务成功率或失败率指标

每个重要改动上线后，应明确：

- 看哪些日志
- 看哪些指标
- 看哪些告警
- 多久内重点观察

## 15. 安全工程规范

### 15.1 基本要求

- 密钥与口令来自安全配置，不入库不入代码
- 遵循最小权限原则
- 敏感信息禁止明文日志输出
- 认证、鉴权、审计逻辑不能被弱化
- 依赖安全扫描要纳入交付流程

### 15.2 高风险点

特别关注：

- 输入校验
- 反序列化
- 文件上传
- 外部回调签名校验
- SQL 注入
- SSRF
- 路径遍历
- 权限绕过

## 16. 稳定性与可靠性规范

分布式系统默认会部分失败，因此设计必须考虑异常场景。

外部调用至少要明确：

- 超时
- 重试
- 幂等
- 降级
- 熔断或限流

异步链路至少要明确：

- 重复消费
- 顺序要求
- 死信处理
- poison message 处理
- 重放安全

## 17. 性能工程规范

- 性能优化必须基于测量，而不是猜想
- 不要为了“也许更快”而牺牲可维护性
- 热点链路关注 SQL 次数、序列化成本、对象分配、远程调用扇出
- 如果为了性能牺牲可读性，必须有可量化收益

## 18. 依赖治理规范

- 新依赖必须有理由
- 避免同类库重复引入
- 优先选择稳定、持续维护的依赖
- 重要升级必须有验证与回滚预案

引入新依赖前至少评估：

- 是否仍在维护
- 安全风险
- 传递依赖影响
- 团队是否掌握

## 19. 配置与环境管理规范

- 环境差异通过配置区分，不通过代码分支区分
- 测试、预发、生产应尽可能同构
- 配置项需可追踪、可审计
- 默认值必须安全
- feature toggle 要有明确生命周期

## 20. 文档更新规范

当改动影响以下内容时，必须同步更新文档：

- 本地开发方式
- 启动方式
- 配置项
- 接口契约
- 运维手册
- 发布步骤
- 数据迁移步骤

## 21. 事故复盘导向

对严重缺陷、线上事故、频繁问题，团队应形成最小闭环复盘：

- 根因是什么
- 为什么没有提前发现
- 是测试缺口、监控缺口还是设计缺口
- 如何通过机制避免再次发生

修复措施优先选择“系统性改进”，而不是“针对这一次打补丁”。

## 22. AI Agent 交付补充要求

当 AI Agent 参与交付时，额外要求如下：

- 必须先阅读本地上下文再改代码
- 必须遵守 `AGENTS.md` 与 `docs/code-rules.md`
- 不做无关大重构
- 明确说明假设
- 如未完成验证，必须诚实说明
- 如涉及契约、数据库、消息、发布风险，必须主动提示

## 23. 企业级落地标准

一个服务或模块，只有满足以下条件，才能认为具备企业级交付基础：

- 限界上下文清晰
- 分层职责明确
- 契约可治理
- 构建与测试可重复
- 发布路径可追踪
- 生产可观测
- 默认安全
- 代码可维护
