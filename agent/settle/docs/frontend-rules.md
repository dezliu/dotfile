# frontend-rules.md

## 1. 文件定位

本文件定义企业级前端项目开发规范，适用于：

- Vue
- 企业后台系统
- 中后台平台
- BFF/API 协作项目
- 使用 AI Agent 辅助开发的前端仓库

本文件关注：

- Vue 项目目录如何组织
- 页面、组件、状态、接口如何分层
- 前端如何和后端契约协作
- 测试、可维护性、性能、发布如何落地

## 2. 基本原则

- 用户可理解性优先于炫技实现
- 页面业务语义优先于临时拼装
- 组件复用建立在清晰边界之上，而不是过度抽象
- 与后端契约稳定协作优先于前端私自猜测字段
- 可测试、可观测、可回滚是企业前端的基本要求

## 3. 技术栈默认约定

默认技术栈建议：

- Vue 3
- TypeScript
- Vue Router
- Pinia
- Axios 或统一请求层封装
- Vitest / Jest
- Playwright / Cypress

如果项目已有既定技术栈，必须优先遵循现有技术选型。

## 4. 推荐目录结构

```text
src
  |- app
  |  |- router
  |  |- store
  |  |- provider
  |
  |- pages
  |  |- order
  |  |  |- list
  |  |  |  |- index.vue
  |  |  |- detail
  |  |     |- index.vue
  |
  |- components
  |  |- business
  |  |- common
  |  |- layout
  |
  |- modules
  |  |- order
  |  |  |- api
  |  |  |- model
  |  |  |- store
  |  |  |- components
  |  |  |- composables
  |
  |- composables
  |- services
  |- utils
  |- constants
  |- styles
  |- assets
  |- types
```

推荐思路：

- `pages` 承载路由页面
- `components` 承载可复用组件
- `modules` 承载按业务域组织的能力
- `services` 承载通用请求封装与跨模块服务
- `composables` 承载复用逻辑

## 5. 分层规则

### 5.1 Page 层

职责：

- 路由入口
- 页面级数据加载
- 页面布局组织
- 与模块能力编排

要求：

- Page 不应堆积大量业务逻辑
- Page 不直接拼接复杂请求参数逻辑
- Page 不直接写大量接口转换逻辑

### 5.2 Component 层

职责：

- 可复用 UI 片段
- 明确输入输出
- 封装交互细节

要求：

- 组件边界清晰
- 通过 props / emits 暴露契约
- 不在通用组件里夹带页面特有业务

组件分类建议：

- 通用组件：无业务语义
- 业务组件：有明确业务领域归属
- 布局组件：页面框架、导航、容器

### 5.3 Module 层

职责：

- 组织某个业务域的前端能力
- 管理 API、模型、状态、业务组件、复用逻辑

要求：

- 以业务域组织，而不是以技术类型无限平铺
- 模块内聚，跨模块依赖保持克制
- 模块间共享逻辑通过公共层显式抽取

### 5.4 Service 层

职责：

- HTTP 请求封装
- 请求拦截、鉴权、重试、错误映射
- 与 BFF / API 契约交互

要求：

- 不在页面里直接散落裸请求
- 请求层统一处理 token、trace、错误码
- 接口字段转换保持集中和显式

## 6. Vue 编码规范

### 6.1 组件规范

- 组件命名应表达业务语义
- 单文件组件应保持职责单一
- 复杂页面拆成多个业务子组件
- 避免超大 `index.vue`

推荐命名：

- `OrderListPage.vue`
- `OrderFilterPanel.vue`
- `OrderStatusTag.vue`
- `BaseTable.vue`

不推荐命名：

- `index2.vue`
- `TempCard.vue`
- `InfoBox.vue`
- `DataPanel.vue`

### 6.2 `script setup` 规范

- 优先使用 `script setup`
- 响应式状态与派生状态分开组织
- 事件处理函数命名清晰
- 避免把整页逻辑塞进一个 setup 块里

### 6.3 composables 规范

- composable 用于复用“状态 + 行为”
- 命名使用 `useXxx`
- 不把页面私有逻辑滥抽成 composable

推荐：

- `useOrderFilters`
- `useOrderTable`
- `usePermissionGuard`

## 7. 状态管理规范

推荐状态分类：

- 全局状态：用户信息、权限、租户、主题
- 模块状态：订单筛选条件、分页状态、详情缓存
- 组件局部状态：弹窗开关、输入中间态

要求：

- 能局部就不要全局
- Pinia store 应按业务域组织
- store 中避免堆放仅页面可见的临时状态
- 异步请求和状态变更要可追踪

## 8. API 契约协作规范

### 8.1 基本要求

- 前端不得擅自猜测接口字段含义
- 前端不得依赖未确认的隐式字段
- 重要接口变更必须和后端同步治理
- 接口返回结构要有统一错误处理策略

### 8.2 建议结构

```text
modules/order/api
  |- queryOrders.ts
  |- getOrderDetail.ts
  |- createOrder.ts
```

### 8.3 DTO / ViewModel 规范

- 接口返回对象与页面展示对象可分离
- 当展示逻辑复杂时，需显式转换为 ViewModel
- 不要在模板里做大量字段拼装

## 9. 权限与安全规范

- 权限控制不能只依赖前端展示隐藏
- 敏感操作必须校验后端权限
- 不在前端代码中硬编码密钥、token、私有地址
- 日志与埋点中避免输出敏感个人信息
- 文件上传、富文本、外链跳转要考虑安全风险

## 10. 可观测性规范

企业前端应具备最小可观测能力：

- 页面错误上报
- 请求失败追踪
- 用户关键行为埋点
- 性能指标采样
- 发布版本标识

要求：

- 错误日志能关联用户、页面、接口、版本
- 埋点命名统一
- 埋点不要与业务代码深度耦合

## 11. 性能规范

- 懒加载页面和大组件
- 控制首屏请求数量
- 避免重复请求
- 长列表优先考虑虚拟滚动
- 避免在模板中做重计算
- 大对象响应式要谨慎

性能优化必须基于真实瓶颈，而不是猜测。

## 12. 测试规范

至少考虑以下测试层：

- 组件单测
- composable 单测
- store 测试
- 页面级交互测试
- 关键链路 E2E 测试

最低建议：

- 复杂交互组件补单测
- 关键下单、审批、登录流程补 E2E
- Bug 修复补回归测试

## 13. 发布与工程规范

- 环境变量分环境管理
- 静态资源版本可追踪
- 发布产物可回滚
- 高风险功能优先 feature flag
- 前端接口变更需同步更新联调说明

## 14. AI Agent 额外要求

当 AI Agent 参与前端开发时，必须：

- 优先复用现有组件与页面模式
- 不擅自引入新的状态管理方案
- 不随意重写页面视觉结构
- 明确说明契约假设
- 变更页面交互时补充验证建议

## 15. 企业级前端就绪标准

一个前端项目只有满足以下条件，才能认为具备企业级基础：

- 页面和模块结构清晰
- 组件边界明确
- 状态管理不混乱
- API 契约可治理
- 发布可追踪
- 错误可观测
- 权限与安全有基本保障
- 关键流程可测试
