# mobile-rules.md

## 1. 文件定位

本文件定义企业级移动端项目开发规范，适用于：

- React Native 跨平台项目
- Android 原生项目
- iOS 原生项目

支持技术栈：

- RN：React Native
- Android：Java / Kotlin
- iOS：Swift / Objective-C

本文件关注：

- 跨平台与原生项目如何分层
- 页面、状态、网络、缓存、设备能力如何治理
- 多端协作如何保持契约一致
- 测试、发布、埋点、稳定性如何落地

## 2. 基本原则

- 用户体验稳定性优先于局部实现技巧
- 跨平台复用建立在边界清晰之上
- 原生能力接入必须可维护、可测试、可降级
- 网络、缓存、权限、埋点属于基础能力，不应散落
- 兼容性和发布可控性是移动端工程基线

## 3. 项目形态建议

### 3.1 RN 跨平台项目

适合：

- 业务页面高度一致
- 迭代速度要求高
- 团队希望复用大部分 UI 和业务逻辑

### 3.2 Android / iOS 原生项目

适合：

- 深度依赖平台能力
- 动画、音视频、硬件、推送链路复杂
- 平台差异显著

### 3.3 混合模式

企业常见方式：

- 主要业务页面使用 RN
- 高性能或深平台能力页面用原生
- 通过桥接模块统一接入

## 5. 分层规范

推荐统一理解为：

- UI 层：页面、组件、交互
- State/ViewModel 层：页面状态、输入输出、展示逻辑
- Domain 层：业务规则、用例、模型
- Data 层：Repository、接口请求、本地缓存
- Platform/Bridge 层：原生能力、设备能力、桥接模块

要求：

- 页面层不直接拼装复杂网络逻辑
- 原生 API 接入不要散落到页面中
- 业务规则不要只写在按钮点击回调里

## 6. RN 项目规范

### 6.1 组件与页面

- Screen 负责页面编排
- Component 负责 UI 复用
- Hook 负责复用状态与行为
- Service 负责请求与基础能力

推荐命名：

- `OrderListScreen`
- `OrderDetailScreen`
- `OrderCard`
- `useOrderList`

### 6.2 状态管理

- 全局状态最小化
- 按业务域拆分 store
- 临时 UI 状态优先局部管理
- 异步加载状态必须清晰区分 `loading / success / empty / error`

### 6.3 原生桥接

- RN 调用原生能力必须通过明确 bridge/module
- bridge 层统一处理平台差异
- 桥接失败要有降级或错误提示

## 7. Android 规范

适用语言：

- Java
- Kotlin

推荐方向：

- 新代码优先 Kotlin
- 旧项目遵循现有选型，不强推一次性迁移

工程要求：

- Activity / Fragment 保持薄
- 业务逻辑进入 ViewModel / UseCase / Domain
- Repository 统一管理网络与本地数据
- 协程或异步处理方式要统一

禁止：

- 在 Activity 中堆大量业务逻辑
- 在 Adapter 中写复杂状态决策
- 网络请求直接散落在多个 UI 类里

## 8. iOS 规范

适用语言：

- Swift
- Objective-C

推荐方向：

- 新代码优先 Swift
- 旧模块可保留 Objective-C，并通过清晰边界与 Swift 协作

工程要求：

- ViewController 保持薄
- 业务逻辑放到 ViewModel / UseCase / Domain
- 网络层、缓存层、桥接层职责清晰
- 平台特有能力通过统一封装暴露

禁止：

- 在 ViewController 中堆复杂业务状态机
- 在网络回调里直接拼页面展示逻辑
- 到处散落通知监听和设备能力调用

## 9. 网络与数据规范

所有端统一要求：

- 网络层统一封装
- 错误码统一映射
- 超时、重试、鉴权逻辑统一处理
- 本地缓存策略显式定义
- 离线与弱网行为可说明

至少明确：

- 请求失败如何提示
- token 过期如何处理
- 幂等请求如何保护
- 本地缓存何时失效

## 10. 权限与设备能力规范

涉及以下能力时必须集中治理：

- 相机
- 相册
- 位置
- 麦克风
- 蓝牙
- 推送
- 文件系统

要求：

- 权限申请时机明确
- 权限拒绝有兜底提示
- 权限逻辑不要散落在多个页面
- 原生能力调用失败需可诊断

## 11. 埋点与可观测性规范

移动端必须具备：

- 崩溃上报
- 关键页面埋点
- 核心流程成功率统计
- 网络错误统计
- 版本与渠道标识

埋点要求：

- 事件名统一
- 属性字段统一
- 不记录敏感信息
- 埋点实现与业务逻辑解耦

## 12. 性能与稳定性规范

重点关注：

- 首屏启动时间
- 页面切换流畅度
- 长列表性能
- 图片与资源加载
- 内存占用
- 崩溃率
- ANR / 卡顿 / freeze

要求：

- 性能优化基于监控和指标
- 大图、长列表、复杂动画要专项评估
- 高频页面避免过度渲染

## 13. 测试规范

至少应考虑：

- 业务逻辑单测
- ViewModel / Hook 测试
- 组件或页面交互测试
- 原生桥接测试
- 关键链路自动化测试

最低建议：

- 登录、下单、支付、审批等核心流程必须可回归
- Bug 修复补回归测试
- bridge 接口变更补兼容性验证

## 14. 发布规范

移动端发布必须考虑：

- 版本号管理
- 渠道管理
- 灰度发布
- 开关控制
- 崩溃监控
- 回滚或紧急修复策略

要求：

- 发布前明确观测指标
- 高风险能力通过远程开关控制
- 与后端接口变更同步安排联调和发布窗口

## 15. 多端协作规范

当 RN、Android、iOS 并行开发时，必须明确：

- 哪些能力跨平台复用
- 哪些能力原生独占
- 桥接接口 owner 是谁
- 接口契约由谁维护
- 发布节奏如何对齐

禁止：

- 三端各自定义一套接口字段语义
- 桥接协议无版本管理
- 页面行为在不同端无说明地不一致

## 16. AI Agent 额外要求

当 AI Agent 参与移动端开发时，必须：

- 优先遵循现有导航、状态管理、网络封装模式
- 不擅自引入新跨平台框架
- 不破坏既有桥接契约
- 对平台差异做显式说明
- 对未能验证的设备行为诚实说明

## 17. 企业级移动端就绪标准

一个移动端项目只有满足以下条件，才能认为具备企业级基础：

- 分层清晰
- 页面与业务模块结构清楚
- 网络与缓存统一治理
- 权限与设备能力可控
- 崩溃与埋点可观测
- 发布可灰度、可追踪
- 多端契约协作稳定
- 核心流程可测试
