# V1.20.0 退款代码逻辑梳理

本文档按当前代码梳理新结算协议退款链路，重点覆盖以下四条路径：

1. `SettlementOrderRefundHandler.handle` 接收上游退款消息并发起退款。
2. 原单正向支付回执落库后，通过 `continueIfNecessary` 继续退款。
3. 原路退款回执落库后，更新逆向支付单并触发逆向单聚合。
4. 转账退款回执落库后，触发逆向单聚合。

## 1. 代码范围

## 2. 分层与职责

`SettlementOrderRefundHandler` 位于 `settle/domain`，是新结算协议退款的领域服务编排入口。它不直接消费 MQ，也不直接处理外部交易回执，而是被 entry/application/domain 层逐级调用：

```text
SettlementOrderRefundConsumer
-> NewOrderAppService.refundSettlementOrder
-> NewOrderDomainService.refundSettlementOrder
-> SettlementOrderRefundHandler.handle
```

主处理器只做三件事：

- 把上游退款消息转成 `SettlementOrderRefundCommand`。
- 委托 `SettlementRefundCoordinator` 处理首次退款或续跑。
- 对已经直接落定的退款动作调用 `CommonCallbackHandler.handleRefund` 补上游退款回执。

退款动作的细分规则在 `SettlementOrderRefundCommand`；事务落库和退款消息发送在 `SettlementRefundResolvedWorkExecutor`；正向支付回执、原路退款回执和转账退款回执都通过各自 message handler 进入，再由 `ORDER_UPDATE` 消息统一触发订单聚合。

## 3. 核心对象

| 对象 | 含义 |
|------|------|
| `originOrder` | 原始结算单，退款消息里的 `originBizCode` 指向它。 |
| `originPayOrder` | 原单下的正向支付单。退款不是整单一刀切，而是按每条 `originPayOrder` 状态拆动作。 |
| `reverseOrder` | 逆向退款单，退款消息里的 `bizCode` 会成为 `reverseOrder.orderCode`。 |
| `reversePayOrder` | 逆向支付单，由已支付成功的 `originPayOrder` 生成，代表一条原路退或转账退执行腿。 |
| `billItem` | 收款侧结算明细。撤销、原路退、转账退会按场景更新原 billItem，转账退还可能新增红字 billItem。 |

当前逆向单退款进度主要用 `reverseOrder.orderStatusEnum` 表达，`reverseOrder.refundStatusEnum` 在构造 reverseOrder 时置为 `null`。

## 4. 入口一：上游退款消息

调用链：

```text
SettlementOrderRefundConsumer.onMessage
-> NewOrderAppServiceImpl.refundSettlementOrder
-> NewOrderDomainServiceImpl.refundSettlementOrder
-> SettlementOrderRefundHandler.handle
```

### 4.1 Consumer 处理

`SettlementOrderRefundConsumer` 监听 `tuxi_hst_settlement_settlement_order_refund_topic`。

消费逻辑：

- 消息为空，直接消费成功。
- 重试次数大于 3，记录日志并消费成功。
- 将 schema 拷贝成 `SettlementOrderRefundMessage`。
- 校验 `bizType / bizCode / originBizCode / objectCode`。
- 使用 `hst_bill_lock_settlement_refund_{objectCode}_{bizCode}` 加分布式锁。
- 调用应用层 `refundSettlementOrder`。
- 可重试 `BusinessException` 返回重试，不可重试业务异常返回成功；未知异常返回重试。

### 4.2 Handler 主流程

`SettlementOrderRefundHandler.handle` 当前流程：

```text
1. 打印退款消息日志
2. new SettlementOrderRefundCommand(message, orderConfig, billItemRepository, billRepository)
3. command.duplicateCheck(orderRepository::queryOrderByOrderCode)
4. command.loadOrigin(orderRepository::queryOrderByOrderCode, payOrderRepository::queryByOrder)
5. command.resolveRefundWork()
6. refundCoordinator.execute(command)
7. sendDirectRefundCallback(command, executionResult)
```

关键点：

- `duplicateCheck` 按 `objectCode + bizCode` 查询 reverseOrder，已存在则抛 `ORDER_DUPLICATE`。
- `loadOrigin` 按 `objectCode + originBizCode` 查询原单和原支付单。
- `resolveRefundWork` 会把原支付单拆成撤销、原路退、转账退三组。
- `handle` 本身不判断原路退还是转账退，具体规则由 command 负责。

## 5. payOrder 分组规则

入口：

```text
SettlementOrderRefundCommand.resolveRefundWork
-> prepareResolvedRefund(originPayOrders)
-> shouldReverseSettlement(originPayOrder)
```

### 5.1 撤销分组

以下支付状态进入 `cancelPayOrders`：

- `CREATE`
- `PENDING_PAY`
- `PAY_FAIL`
- `NO_PAY`

执行结果：

- 原 `originPayOrder.payStatusEnum` 更新为 `NO_PAY`。
- 原 `originPayOrder.refundStatusEnum` 更新为 `NO_REFUND`。
- 如果能查到原 billItem，则将其改为未结算、未支付、`SPECIAL_ORIGIN_REFUND`。
- 不生成 `reversePayOrder`。

### 5.2 等待正向结果

如果存在 `originPayOrder.payStatusEnum == PAYING`，该支付单不会进入任何退款动作分组。

协调器会让 reverseOrder 保持或进入 `PAYING`，等待后续正向支付回执通过 `ORDER_UPDATE` 唤醒 `continueIfNecessary`。

注意：当前代码里 `continueIfNecessary` 并没有显式校验 `reverseOrder.extParams.reverseAction=WAIT_RESULT`，而是通过 `OrderUpdateMessageHandlerImpl` 在原单 `refundStatusEnum == REFUNDING` 时触发续跑。

### 5.3 原路退分组

已支付成功且未处于 `REFUNDING / REFUND_SUCCESS` 的支付单会继续判断原路退还是转账退。

走原路退的条件：

- 收款方类型是 `TUXI`。
- 或非总部收款，但对应 billItem 不存在或没有 `billNo`。
- 或 `COURIER_SITE_DELIVERY_FEE` 场景下，日账单对应的月账单尚未 `SETTLED`。

执行结果：

- 原 `originPayOrder.refundStatusEnum` 更新为 `REFUNDING`。
- 如果原 billItem 存在，则改为未结算、退款中、`SPECIAL_ORIGIN_REFUND`。
- 生成原路退 `reversePayOrder`，其 `originPayCode` 指向原支付单 `payCode`，`bizType` 使用原支付单 `bizType`。
- 事务提交后发送 `GENERIC_REFUND`，`refundType=REFUND`。

### 5.4 转账退分组

走转账退的条件：

- 原支付单是 `OFFLINE_PAY_SUCCESS`。
- 或非总部收款且 billItem 已进入已结算账单。
- 或其他存在 billNo 且不满足“结算前原路退”的场景。

执行结果：

- 线下支付成功：原 `originPayOrder.refundStatusEnum` 直接更新为 `REFUND_SUCCESS`。
- 异步转账退：原 `originPayOrder.refundStatusEnum` 更新为 `REFUNDING`。
- 原 payOrder 对应 billItem 标记为 `TRANSFER_REFUND`。
- 生成转账退 `reversePayOrder`，`bizType` 使用退款配置 `refundBizType`。
- 非线下直退且收款方不是 `TUXI` 时，新增红字 billItem，标记为 `TRANSFER_REFUND_RED_BACK`。
- 非线下直退的 reversePayOrder 事务提交后发送 `GENERIC_REFUND`，`refundType=TRANSFER`。

## 6. 协调器执行逻辑

入口：

```text
SettlementRefundCoordinator.execute(command)
```

### 6.1 首次处理

当 `command.reverseOrder == null`：

- 如果存在 `PAYING` 的原支付单，先构造等待态 reverseOrder，并进入等待轮次。
- 如果没有 `PAYING`，按当前分组创建已落定 reverseOrder。

reverseOrder 初始状态：

- 有原路退或转账退：`PAYING`。
- 只有撤销：`NO_PAY`。
- 只有线下直退转账退：执行器中会改为 `OFFLINE_PAY_SUCCESS`。

### 6.2 仍在等待

当已有 reverseOrder 且仍存在 `PAYING` 原支付单：

- 重新按当前原支付单状态准备退款分组。
- 已落定的撤销、原路退、转账退分组仍会执行。
- reverseOrder 保持 `PAYING`。
- 原单退款状态保持 `REFUNDING`。

### 6.3 等待结束但无退款动作

当已有 reverseOrder、无 `PAYING` 原支付单，并且当前没有任何撤销/原路退/转账退分组：

- reverseOrder 更新为 `NO_PAY`。
- reverseOrder 清理 `extParams`。
- originOrder.refundStatusEnum 更新为 `NO_REFUND`。

### 6.4 等待结束且有退款动作

当已有 reverseOrder、无 `PAYING` 原支付单，并且当前形成退款动作：

- reverseOrder.orderAmount 暂按 originOrder.orderAmount 设置。
- 清理 reverseOrder 等待上下文。
- 交给 `SettlementRefundResolvedWorkExecutor` 执行落库和发消息。

## 7. 已落定分组执行器

入口：

```text
SettlementRefundResolvedWorkExecutor.execute(command, reverseOrder, keepReverseOrderPaying, keepOriginRefunding)
```

执行器先构造：

- 原路退 reversePayOrder 列表。
- 转账退 reversePayOrder 列表。
- 转账退红字 billItem 列表。

然后计算 reverseOrder 状态：

| 条件 | reverseOrder.orderStatusEnum |
|------|------------------------------|
| `keepReverseOrderPaying == true` 或存在异步原路退/异步转账退 | `PAYING` |
| 只有线下直退转账退 | `OFFLINE_PAY_SUCCESS` |
| 没有异步退款动作 | `NO_PAY` |

事务内顺序：

```text
1. 保存或更新 reverseOrder
2. 撤销未支付 originPayOrder
3. 标记原路退 originPayOrder 为 REFUNDING
4. 标记转账退 originPayOrder 为 REFUNDING 或 REFUND_SUCCESS
5. 保存原路退 reversePayOrder
6. 保存转账退 reversePayOrder
7. 保存转账退红字 billItem
8. 更新 originOrder.refundStatusEnum
9. 必要时再次更新 reverseOrder
```

事务提交后：

- 有原路退分组时，发送原路退款消息。
- 有异步转账退分组时，发送转账退款消息。

## 8. 直接上游回执

`SettlementOrderRefundHandler.sendDirectRefundCallback` 在 `handle` 和 `continueIfNecessary` 执行协调器后都会调用。

当前逻辑：

```text
1. executionResult 为空或 reverseOrder 为空，直接返回
2. 优先取 executionResult.getReversePayOrders()
3. 如果 reversePayOrders 为空，再取 command.getCancelPayOrders()
4. 调用 commonCallbackHandler.handleRefund(reverseOrder, callbackPayOrders, orderBizConfig)
```

因此：

- 撤销场景没有交易侧异步退款回执，由这里直接补退款回执。
- 线下直退生成的 reversePayOrder 已经是成功状态，也会通过这里尝试补退款回执。
- 如果同一轮既有 reversePayOrder 又有 cancelPayOrders，当前代码优先使用 reversePayOrders 做回执判断。

`CommonCallbackHandler.handleRefund` 的回执条件：

- payOrders 为空直接返回。
- 读取订单配置里的 `callbackCondition`，不满足则不回调。
- 单条 payOrder 且状态仍是 `CREATE / PENDING_PAY / PAYING`，不回调。
- 单条 payOrder 已落定时回调成功或失败。
- 多条 payOrder 必须全部支付成功或线下支付成功才回调；否则跳过。

## 9. 入口二：原单支付回执触发继续退款

用户关心链路：

```text
PayGenericTradeResMessageHandlerImpl
-> handle
-> handleTradeResultNew
-> PayTradeResultCommand.postProcessAfterCallback
-> OrderUpdateTradeCallbackHandler
-> OrderUpdateMessageHandlerImpl
-> settlementOrderRefundHandler.continueIfNecessary
```

详细过程：

1. `PayGenericTradeResMessageHandlerImpl.handle` 收到 `PayGenericTradeRes`。
2. 按 `PayGenericTradeRes:{bizCode}` 加 Redis 锁。
3. 如果 `tradeConfig.isNewTrade(res.getBizType())` 为 true，进入 `handleTradeResultNew`。
4. `handleTradeResultNew` 构造 `PayTradeResultCommand`。
5. 如果回执表类型是 `PAY_ORDER` 或为空：
   - 查询 `HstPayOrder`。
   - 调用 `PayTradeResultCommand.updatePayOrder` 更新正向支付结果。
6. `cmd.postProcessAfterCallback()` 根据交易配置执行回调处理器，默认包含 `OrderUpdateTradeCallbackHandler`。
7. `OrderUpdateTradeCallbackHandler.handle(PayTradeResultCommand)` 发送 `ORDER_UPDATE` 消息，消息体是 `objectCode + orderCode`。
8. `OrderUpdateMessageHandlerImpl.handle` 查询 order。
9. 如果 order 是原单，即 `originOrderCode` 为空：
   - 汇总原单下 payOrder。
   - `order.updateBy(sum)` 更新原单正向支付聚合状态。
   - 更新数据库。
   - 如果原单 `refundStatusEnum == REFUNDING`，调用 `settlementOrderRefundHandler.continueIfNecessary(order)`。
10. `continueIfNecessary` 根据原单号查询 reverseOrder，再按最新 originPayOrders 重新分组并执行协调器。

这条链路用于处理退款发起时仍有 `PAYING` 的原支付单。正向支付回执把原支付单从 `PAYING` 推进到成功、失败或不支付后，退款流程才知道该条 payOrder 应该撤销、原路退还是转账退。

## 10. 入口三：原路退款回执

用户关心链路：

```text
OriginRefundResultMessageHandlerImpl
-> handle
-> handleResult
-> PayOriginRefundTradeResultCommand.postProcessAfterCallback
-> UpdatePayOrderRefundHandler
-> OrderUpdateTradeCallbackHandler
-> OrderUpdateMessageHandlerImpl
-> 逆向逻辑
```

详细过程：

1. `OriginRefundResultMessageHandlerImpl.handle` 收到 `OriginRefundResultMessage`。
2. 按 `PayTradeRefundResult:{bizType}` 加 Redis 锁。
3. `handleResult` 判断 `tradeConfig.isNewTrade(message.getBizType())`。
4. 新交易走 `PayOriginRefundTradeResultCommand`：
   - 按 `payOrderTableKey`，没有则用 `payObjectCode`，查询原 `originPayOrder`。
   - 调用 `postProcessAfterCallback`。
5. `TradeOriginRefundCallbackHandlerEnum` 默认先执行 `UpdatePayOrderRefundHandler`，再执行 `OrderUpdateTradeCallbackHandler`。

`UpdatePayOrderRefundHandler` 的处理：

- 如果原支付单退款状态已是 `PART_REFUND / REFUND_SUCCESS`，直接返回，避免重复处理。
- 回执成功：
  - 如果 `refundAmount` 小于 `payAmount`，原支付单置为 `PART_REFUND`。
  - 否则置为 `REFUND_SUCCESS`。
  - 写入 `refundTime` 和 `thirdRefundTradeNo`。
- 回执失败：原支付单置为 `REFUND_FAIL`。
- 更新原支付单退款结果。
- 通过 `queryPayOrderByOriginPayCode(originPayOrder.objectCode, originPayOrder.payCode)` 查询对应 reversePayOrder。
- 查不到 reversePayOrder，说明不是新结算退款场景，记录日志后返回。
- 查到 reversePayOrder 后：
  - 设置到 command，供后续 handler 使用。
  - 成功则 reversePayOrder.payStatusEnum = `PAY_SUCCESS`。
  - 失败则 reversePayOrder.payStatusEnum = `PAY_FAIL`。
  - reversePayOrder.payTime = originPayOrder.refundTime。
  - reversePayOrder.thirdTradeNo = originPayOrder.thirdRefundTradeNo。
  - 调用 `buildUpdaterForOriginAndTransferRefundResult` 更新 reversePayOrder。

`OrderUpdateTradeCallbackHandler.handle(PayOriginRefundTradeResultCommand)` 的处理：

- 如果 command 中没有 reversePayOrder，直接返回。
- 如果有 reversePayOrder，发送 `ORDER_UPDATE`，消息体是 reversePayOrder 的 `objectCode + orderCode`。

随后 `OrderUpdateMessageHandlerImpl` 进入逆向逻辑。

## 11. 入口四：转账退款回执

用户关心链路：

```text
PayGenericTradeResMessageHandlerImpl
-> handle
-> handleTradeResultNew
-> PayTradeResultCommand.postProcessAfterCallback
-> OrderUpdateTradeCallbackHandler
-> OrderUpdateMessageHandlerImpl
-> 逆向逻辑
```

转账退发送的是 `GENERIC_REFUND`，但回执进入通用交易回执 `PayGenericTradeResMessageHandlerImpl`。

详细过程：

1. `PayGenericTradeResMessageHandlerImpl.handle` 收到转账退回执。
2. 新交易进入 `handleTradeResultNew`。
3. 表类型是 `PAY_ORDER` 或为空时，按 `payOrderTableKey` 或 `objectCode` 加 `bizCode` 查询 reversePayOrder。
4. `PayTradeResultCommand.updatePayOrder` 调用 `HstPayOrder.updateBy(res)`：
   - 成功：reversePayOrder.payStatusEnum = `PAY_SUCCESS`，写入 thirdTradeNo、tradeCode、payTime、账户字段等。
   - 失败：reversePayOrder.payStatusEnum = `PAY_FAIL`；如果支持重试或错误码是 `701`，置为 `NO_PAY`。
5. `postProcessAfterCallback` 执行 `OrderUpdateTradeCallbackHandler`。
6. `OrderUpdateTradeCallbackHandler` 发送 reversePayOrder 所属 reverseOrder 的 `ORDER_UPDATE`。
7. `OrderUpdateMessageHandlerImpl` 查询到 reverseOrder 后进入逆向逻辑。

## 12. ORDER_UPDATE 的正向与逆向分支

`OrderUpdateMessageHandlerImpl.handle` 是支付/退款回执后的订单聚合入口。

### 12.1 正向分支

判断条件：

```text
order.originOrderCode 为空
```

处理：

- 汇总原单下 payOrder。
- 更新原单正向支付汇总状态。
- 如果原单正在退款，即 `refundStatusEnum == REFUNDING`，调用 `continueIfNecessary`。

### 12.2 逆向分支

判断条件：

```text
order.originOrderCode 不为空
```

处理：

```text
1. 查询 reverseOrder 下所有 reversePayOrder
2. updateReverseOrder(reverseOrder, reversePayOrders)
3. 根据 reverseOrder.orderType 查询订单配置
4. commonCallbackHandler.handleRefund(reverseOrder, reversePayOrders, orderBizConfig)
```

逆向单聚合规则：

| reversePayOrder 状态 | 聚合含义 |
|----------------------|----------|
| `PAYING / CREATE / PENDING_PAY` | 仍在处理中 |
| `PAY_SUCCESS / OFFLINE_PAY_SUCCESS` | 成功腿 |
| `PAY_FAIL / NO_PAY` | 失败腿 |

聚合结果：

| 条件 | reverseOrder.orderStatusEnum |
|------|------------------------------|
| reversePayOrders 为空 | `NO_PAY` |
| 存在处理中 | `PAYING` |
| 有失败且没有成功 | `PAY_FAIL` |
| 有成功且没有失败 | `PAY_SUCCESS` |
| 成功失败混合 | `PAY_SUCCESS` |

如果全部落定，reverseOrder.payTime 取所有 reversePayOrder.payTime 的最大值。最后调用 `orderRepository.updateOrder(reverseOrder.buildOrderUpdater())`。

聚合后，`CommonCallbackHandler.handleRefund` 决定是否给上游发送退款回执。多条 reversePayOrder 时，必须全部成功才会回调；单条 reversePayOrder 时，只要不在处理中，就会按成功或失败回调。

## 13. 状态流转汇总

### 13.1 originOrder

| 场景 | refundStatusEnum |
|------|------------------|
| 退款处理中或等待正向支付结果 | `REFUNDING` |
| 只有撤销或等待结束无退款动作 | `NO_REFUND` |
| 只有线下直退且无异步退款动作 | `REFUND_SUCCESS` |

### 13.2 originPayOrder

| 场景 | payStatusEnum | refundStatusEnum |
|------|---------------|------------------|
| 未支付撤销 | `NO_PAY` | `NO_REFUND` |
| 正向支付仍处理中 | `PAYING` | 暂不改变，由后续续跑处理 |
| 原路退发起后 | 保留正向支付状态 | `REFUNDING` |
| 原路退回执成功 | 保留正向支付状态 | `REFUND_SUCCESS` 或 `PART_REFUND` |
| 原路退回执失败 | 保留正向支付状态 | `REFUND_FAIL` |
| 异步转账退发起后 | 保留正向支付状态 | `REFUNDING` |
| 线下直退 | `OFFLINE_PAY_SUCCESS` | `REFUND_SUCCESS` |

### 13.3 reverseOrder

| 场景 | orderStatusEnum |
|------|-----------------|
| 有异步退款腿处理中 | `PAYING` |
| 只有撤销或无实际退款动作 | `NO_PAY` |
| 只有线下直退 | `OFFLINE_PAY_SUCCESS`，后续逆向聚合按成功处理 |
| 逆向聚合全失败 | `PAY_FAIL` |
| 逆向聚合全成功 | `PAY_SUCCESS` |
| 逆向聚合部分成功部分失败 | `PAY_SUCCESS` |

### 13.4 reversePayOrder

| 场景 | 初始状态 | 回执后状态 |
|------|----------|------------|
| 原路退 | `PAYING` | `PAY_SUCCESS / PAY_FAIL` |
| 转账退 | `PAYING` | `PAY_SUCCESS / PAY_FAIL / NO_PAY` |
| 线下直退 | `OFFLINE_PAY_SUCCESS` | 无需异步回执 |

## 14. 幂等与重复处理

当前代码里的主要幂等点：

- `SettlementOrderRefundConsumer` 使用 `objectCode + bizCode` 分布式锁拦截并发消费。
- `SettlementOrderRefundHandler.handle` 对已存在 reverseOrder 抛 `ORDER_DUPLICATE`。
- `SettlementOrderRefundCommand.isRefundablePaidSuccess` 会跳过已处于 `REFUNDING / REFUND_SUCCESS` 的原支付单。
- `UpdatePayOrderRefundHandler` 会跳过已 `PART_REFUND / REFUND_SUCCESS` 的原支付单。
- 原路退回执只有查到对应 reversePayOrder 时，才触发 reverseOrder 的 `ORDER_UPDATE`。

需要注意：

- `handle` 不是重复退款消息的恢复入口，已存在 reverseOrder 会直接重复单异常。
- `continueIfNecessary` 当前不显式检查 reverseOrder 的 WAIT_RESULT 标记，触发条件主要来自原单 `refundStatusEnum == REFUNDING`。
- 多条 reversePayOrder 的上游退款回执要求全部成功；部分失败时 reverseOrder 会聚合为 `PAY_SUCCESS`，但 `CommonCallbackHandler` 不会对多腿部分成功发送成功回执。

## 16. 测试与验证建议

当前可重点回归：

- 首次退款消息下，未支付、支付中、已支付未结算、已结算 payOrder 混合分组是否正确。
- 原单 `PAYING` 回执后是否能触发 `continueIfNecessary`。
- 原路退回执是否同时更新 originPayOrder 和 reversePayOrder。
- 转账退回执是否能更新 reversePayOrder 并触发 reverseOrder 聚合。
- 多 reversePayOrder 全成功、全失败、处理中、成功失败混合时 reverseOrder 状态是否符合预期。
- 单腿失败、多腿部分失败时，上游退款回执是否符合业务预期。

## 17. 总结

当前退款链路的核心模型是：

```text
按 originPayOrder 拆退款动作
-> 按 cancel / origin refund / transfer refund 分组
-> 用 reverseOrder 承载逆向单
-> 用 reversePayOrder 承载异步退款腿
-> 交易回执统一通过 ORDER_UPDATE 触发 reverseOrder 聚合
-> CommonCallbackHandler 决定是否给上游发送退款回执
```

`SettlementOrderRefundHandler` 是入口编排器，不是所有退款规则的承载点。真正的分组判断在 `SettlementOrderRefundCommand`，等待态和续跑由 `SettlementRefundCoordinator` 编排，事务落库和退款消息发送由 `SettlementRefundResolvedWorkExecutor` 完成，回执后的最终状态聚合由 `OrderUpdateMessageHandlerImpl` 的逆向分支完成。
