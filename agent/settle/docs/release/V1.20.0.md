# V1.20.0：新结算协议订单与退款链路接入说明

本文档基于当前代码实现，梳理 `SettlementOrderConsumer` 与 `SettlementOrderRefundConsumer` 两条 MQ 链路的业务逻辑、代码流程、配置扩展点和新场景接入注意事项。

适用范围：

- 正向新结算协议建单：`tuxi_hst_settlement_receive_settlement_order_topic`
- 逆向新结算协议退款：`tuxi_hst_settlement_settlement_order_refund_topic`
- 面向后续新增 `bizType` 场景的研发、测试、联调与发布评估

## 1. 总体入口

| 链路 | Consumer | Topic | Consumer Group | 应用入口 |
|------|----------|-------|----------------|----------|
| 正向建单 | `SettlementOrderConsumer` | `tuxi_hst_settlement_receive_settlement_order_topic` | `tuxi_hst_settlement_receive_settlement_order_consumer` | `NewOrderAppService#createSettlementOrder` |
| 退款建单 | `SettlementOrderRefundConsumer` | `tuxi_hst_settlement_settlement_order_refund_topic` | `tuxi_hst_settlement_settlement_order_refund_consumer` | `NewOrderAppService#refundSettlementOrder` |

两个 Consumer 都属于 entry 层，只负责 MQ 边界处理：

- 反序列化 schema 消息
- 必填参数校验
- 消费重试次数上限控制
- 分布式锁防并发重复处理
- 调用 application 层入口
- 根据异常类型决定 ACK 或 RETRY

真正的业务规则落在 domain 层：

- 正向建单：`SettlementCreateOrderCommand`
- 退款建单：`SettlementOrderRefundCommand`
- 退款编排：`SettlementRefundCoordinator`
- 已落定退款动作执行：`SettlementRefundResolvedWorkExecutor`

## 2. Consumer 通用机制

### 2.1 重试次数

两个 Consumer 都通过 `MQMsgEnum.RECONSUME_TIMES` 获取 MQ 重试次数。

当前策略：

- `reconsumeTimes > 3`：记录错误日志并返回 `SUCCEED`，消息不再继续重试。
- `BusinessException`：
  - 如果 `ErrorCodeEnum#isRetry()` 为 true，返回 `RETRY`。
  - 其他业务异常返回 `SUCCEED`，避免不可恢复参数或配置问题反复重试。
- 普通异常：
  - 正向建单 Consumer：记录错误后返回 `SUCCEED`。
  - 退款 Consumer：记录错误后返回 `RETRY`。

接入新场景时需要特别注意：正向建单链路中非 `BusinessException` 的未知异常不会触发 MQ 重试，应优先通过配置校验、联调测试和日志告警提前发现。

### 2.2 分布式锁

正向建单锁：

```text
hst_settlement_order_lock_settlement_{bizType}_{objectCode}_{bizCode}
```

退款建单锁：

```text
hst_bill_lock_settlement_refund_{objectCode}_{bizCode}
```

锁超时时间均为 100 秒。未抢到锁时直接返回 `SUCCEED`，视为并发重复消息。

锁只解决同一时刻的重复消费，不等同于业务幂等。业务幂等仍依赖 domain 层重复校验：

- 正向建单：按 `objectCode + bizCode` 查询是否已有订单。
- 退款建单：按 `objectCode + bizCode` 查询是否已有逆向订单。

## 3. 正向建单业务流程

### 3.1 消息字段

正向消息先从 schema copy 到 `SettlementOrderMessage`：

| 字段 | 含义 | 校验 |
|------|------|------|
| `bizType` | 业务场景类型，用于查 `order.bizConfig` | 必填 |
| `bizCode` | 上游业务唯一编号，也是本系统订单 `orderCode` | 必填 |
| `businessTime` | 业务发生时间 | 必填 |
| `amount` | 结算金额，单位元 | 必填，大于 0，最多 2 位小数 |
| `objectCode` | 结算对象/分库分表键 | 必填 |
| `payObjectCode` | 付款对象 | 可空，后续可由配置表达式兜底 |
| `payObjectType` | 付款对象类型 | 可空，后续可由配置表达式兜底 |
| `recObjectCode` | 收款对象 | 可空，后续可由配置表达式兜底 |
| `recObjectType` | 收款对象类型 | 可空，后续可由配置表达式兜底 |
| `deadLine` | 支付截止时间 | 可空 |
| `extParams` | 场景扩展 JSON 字符串 | 空串会归一为 null |

### 3.2 调用链

```text
SettlementOrderConsumer.onMessage
→ BeanUtil.copyProperties(schema, SettlementOrderMessage)
→ SettlementOrderMessage.validateRequiredParams
→ Redis tryLock
→ NewOrderAppServiceImpl.createSettlementOrder
→ NewOrderDomainServiceImpl.createSettlementOrder
→ new SettlementCreateOrderCommand(message, orderConfig)
→ duplicateCheck
→ createOrder
→ splitOrder
→ transaction(save order + payOrders)
→ processAfterCreation
```

### 3.3 建单规则

`SettlementCreateOrderCommand#createOrder` 会生成 `HstOrder`：

- `orderCode = message.bizCode`，对外业务唯一编号保持来自上游。
- `bizCode = UniqueCodeGeneratorUtil.generateUniqueCode()`，作为系统内部子业务编号。
- `orderType = message.bizType`。
- `orderAmount = message.amount`。
- `orderName = order.bizConfig[bizType].name`，为空时回退为 `bizType`。
- `orderStatusEnum = PENDING_PAY`。
- `objectCode / businessTime / deadLine / payObject / recObject / extParams` 来自消息。
- `extField1 / extField2 / extField3 / sourceOrderInfo / dimension / bizOrderCode` 可通过配置固定值或 QLExpress 表达式生成。

配置解析优先级：

```text
{key}Value 存在 → 直接使用固定值
{key}Express 存在 → 使用 QLExpress 从上下文计算
都不存在 → null
```

表达式上下文：

```text
order   当前 HstOrder
message 当前 SettlementOrderMessage
```

支持的订单字段配置键：

- `extField1Value` / `extField1Express`
- `extField2Value` / `extField2Express`
- `extField3Value` / `extField3Express`
- `sourceOrderInfoValue` / `sourceOrderInfoExpress`
- `dimensionValue` / `dimensionExpress`
- `bizOrderCodeValue` / `bizOrderCodeExpress`

## 4. 正向拆单扩展点

### 4.1 splitHandler

正向建单通过 `order.bizConfig.{bizType}.splitHandler` 选择 `OrderSplitStrategyEnum`。

当前枚举：

| 枚举 | 说明 | Handler |
|------|------|---------|
| `CABINET_SPLIT` | 柜机分润 | `CabinetOrderSplitHandler` |
| `CABINET_OVERFLOW_SPLIT` | 柜机超期分润 | `CabinetOvertimeOrderSplitHandler` |
| `DIRECT_DELIVERY_INSTALLMENT` | 直投分期 | `DirectDeliveryInstallmentSplitHandler` |
| `ONE` | 一个 order 对应一个 payOrder | `OneOrderSplitHandler` |
| `AD_ORDER_AMOUNT_SPLIT` | 广告金额拆分 | `ADOrderAmountSplitHandler` |
| `COMMON` | 新结算协议通用拆单 | `CommonOrderSplitHandler` |

新结算协议接入优先使用 `COMMON`。只有确实存在复杂拆分规则时，才新增 `NewOrderSplitHandler` 实现并注册到 `OrderSplitStrategyEnum`。

### 4.2 COMMON 拆单规则

`CommonOrderSplitHandler` 默认生成 1 条 `HstPayOrder`，金额等于订单金额。

可配置项：

| 配置 | 作用 |
|------|------|
| `payObject` | 固定付款方 |
| `payObjectType` | 固定付款方类型 |
| `recObject` | 固定收款方 |
| `recObjectType` | 固定收款方类型 |
| `bizType` | 固定交易 bizType |
| `bizTypeMap` | 按表达式结果映射交易 bizType |
| `props.payObjectExpress` | 计算付款方 |
| `props.payObjectTypeExpress` | 计算付款方类型 |
| `props.recObjectExpress` | 计算收款方 |
| `props.recObjectTypeExpress` | 计算收款方类型 |
| `props.objectExpress` | 计算 payOrder 分表键 |
| `props.bizTypeKeyExpress` | 计算 `bizTypeMap` 的 key |

COMMON 拆单的表达式上下文：

```text
order    当前 HstOrder
payOrder 当前 HstPayOrder
```

COMMON 拆单兜底逻辑：

- 付款方未配置固定值且无表达式时，取 `order.payObject`。
- 收款方未配置固定值且无表达式时，取 `order.recObject`。
- 分表键未配置表达式时，取 `order.objectCode`。
- 付款方/收款方类型未配置固定值且无表达式时，分别取 `order.payObjectType` / `order.recObjectType`。
- `bizType` 未固定配置时，可通过 `bizTypeKeyExpress + bizTypeMap` 动态选择。

拆单后会校验：

- `payAmount` 汇总必须等于 `orderAmount`。
- `bizType / payObject / recObject / objectCode / payObjectType / recObjectType` 必须非空。

## 5. 正向后置处理扩展点

正向建单保存订单和支付单后，执行：

```text
OrderCreateFinishEnum.handle(command, orderBizConfig.postHandler)
```

默认处理器：

```text
SAVE_BILL_ITEM,PAY
```

如果 `postHandler` 配置了额外处理器，会追加执行；已在默认列表中的不会重复执行。

### 5.1 SAVE_BILL_ITEM

`SaveBillItemHandler` 负责创建收款侧 `bill_item`。

关键配置：

- `order.bizConfig.{bizType}.needBillItem`
  - false：不创建 billItem。
  - true：按 payOrder 创建 billItem。
- `order.bizConfig.{bizType}.sendBillMsg`
  - true 且只有一条 billItem：发送 `tuxi_hst_single_bill_kafka_topic` 触发单账单创建。
  - 多条 billItem 时当前不支持自动发送单账单消息。
- `trade.bizConfig.{payOrder.bizType}.billType`
  - 用于写入 `BillItem.bizType`。
- `trade.bizConfig.{payOrder.bizType}.dimensionExpress`
  - 用于计算 billItem 维度。

### 5.2 PAY

`SendPayTradeMessageHandler` 负责支付动作。

支付方式由 `order.bizConfig.{bizType}.props` 控制：

| 配置 | 作用 |
|------|------|
| `pay` | 无条件支付策略 |
| `payCondition` | 支付条件表达式 |
| `payConditionMatched` | 条件命中后的支付策略 |
| `payConditionUnMatched` | 条件未命中后的支付策略 |

支付策略取值：

| 取值 | 行为 |
|------|------|
| `online` | 更新 payOrder 为 `PAYING`，发送交易 MQ |
| `offline` | 直接把 order/payOrder 更新为 `OFFLINE_PAY_SUCCESS` |
| `success` | 直接把 order/payOrder 更新为 `PAY_SUCCESS` |
| `no` | 直接把 order/payOrder 更新为 `NO_PAY` |
| 空或其他 | 默认按 `online` 处理 |

在线支付还会检查：

- `payOrder.canPay()`：计划时间已到且未超过截止时间。
- `order.canRePayStatus`：当前状态是否允许发起支付。
- `HwtAccountConfig#bankAccountGrayAccount`：付款方或收款方是否命中灰度。
- Redis 支付处理锁：`order:pay:handle:lock:{payCode}`，默认锁定 `order.payHandleLockMinutes` 分钟。

发送交易 MQ 时：

- 默认 topic：`tuxi_hwt_trade_generic_topic`
- 如果 `common.commonGenericTradeTopicConfig[billType]` 配置了 topic，则按 billType 路由。
- MQ body：`GenericTradeMessage.newMessage("GENERIC_TRADE", payOrder.buildPayGenericTradeMessage(...))`
- MQ key：由 `trade.bizConfig.{tradeBizType}.tradeMessageKey` 决定，参考 `TradeMessageKeyTypeEnum`。

交易请求扩展点：

- `trade.bizConfig.{tradeBizType}.billItemTablekey`
- `trade.bizConfig.{tradeBizType}.payOrderTablekey`
- `trade.bizConfig.{tradeBizType}.tradeExtParam`

这些配置均通过 QLExpress 从 `order/payOrder` 上下文计算。

### 5.3 COMMON_CALLBACK

`CommonCallbackHandler` 可作为正向后置处理器，也可在交易回调后触发。

配置入口：

- `order.bizConfig.{bizType}.postHandler=COMMON_CALLBACK`
- `order.bizConfig.{bizType}.props.callbackCondition`
- `order.bizConfig.{bizType}.props.callbackMqTags`
- `order.bizConfig.{bizType}.props.callbackExtParam_{key}`

回执逻辑：

- 单 payOrder：
  - `CREATE/PENDING_PAY/PAYING` 不回执。
  - 其他状态按成功或失败发送回执。
- 多 payOrder：
  - 只有全部支付成功才回执。
  - 回执按订单维度发送，`tradeCode/thirdTradeCode` 置空。
- 回执 topic 使用 `ZmsUtils.sendWithSchema(tags, bizCode, schema, null)`。
- `tags` 默认取原始 `bizType`，可通过 `callbackMqTags` 覆盖。

`callbackExtParam_{key}` 会把表达式结果写入回执 schema 的 `extParams`。

### 5.4 PROFIT_SHARING

`ProfitSharingHandler` 可用于推送分润报表。

配置入口：

- `order.bizConfig.{bizType}.postHandler=PROFIT_SHARING`
- `order.bizConfig.{bizType}.props.depotCodeExpress`
- `order.bizConfig.{bizType}.props.profitSharingSceneType`

当前仅支持 `recObjectType=AGENT/TUXI` 的订单。正向建单按收入方向 `REC` 推送，退款后置按支出方向 `PAY` 推送。

## 6. 退款业务流程

### 6.1 消息字段

退款消息先从 schema copy 到 `SettlementOrderRefundMessage`：

| 字段 | 含义 | 校验 |
|------|------|------|
| `bizType` | 退款业务类型，用于查 `order.bizConfig` | 必填 |
| `bizCode` | 逆向退款单号，也是 reverseOrder 的 `orderCode` | 必填 |
| `originBizCode` | 原正向结算单号 | 必填 |
| `objectCode` | 结算对象/分库分表键 | 必填 |

### 6.2 调用链

```text
SettlementOrderRefundConsumer.onMessage
→ BeanUtil.copyProperties(schema, SettlementOrderRefundMessage)
→ SettlementOrderRefundMessage.validateRequiredParams
→ Redis tryLock
→ NewOrderAppServiceImpl.refundSettlementOrder
→ NewOrderDomainServiceImpl.refundSettlementOrder
→ new SettlementOrderRefundCommand(message, orderConfig, billItemRepository, billRepository)
→ duplicateCheck
→ loadOrigin
→ resolveRefundWork
→ execute(SettlementRefundCoordinator::execute)
→ processAfterCreation
```

### 6.3 幂等与重复消息

当前代码的业务幂等策略：

- `SettlementOrderRefundCommand#duplicateCheck` 会查询 `objectCode + bizCode` 是否已存在 reverseOrder。
- 如果已存在，会抛出 `ORDER_DUPLICATE`。
- Consumer 捕获到非 retry 的 `BusinessException` 后返回 `SUCCEED`。

因此，当前实现对同一 `bizCode` 的重复退款消息是“直接 ACK 丢弃”，不会补发已落库但未发送成功的退款 MQ。新场景如要求“落库成功但发消息失败后可恢复”，需要另行补充恢复逻辑或补偿任务。

## 7. 退款分组规则

`SettlementOrderRefundCommand#resolveRefundWork` 会按原单下每条 `originPayOrder` 当前状态拆分为三类工作：

| 分组 | 条件 | 后续动作 |
|------|------|----------|
| `cancelPayOrders` | `CREATE/PENDING_PAY/PAY_FAIL/NO_PAY` 且未处理过退款 | 原支付单置 `NO_PAY`，billItem 改为不结算 |
| `refundOriginPayOrders` | 支付成功，且不需要逆向结算 | 发送原路退款 |
| `refundTransferPayOrders` | 支付成功，且需要逆向结算 | 创建 reverse payOrder / 红字 billItem，发送转账退款 |

已经处理过退款的原 payOrder 会跳过：

- `REFUNDING`
- `REFUND_SUCCESS`
- `PART_REFUND`
- `NO_REFUND`

未支付分组不会创建 reverse payOrder，只会更新原 payOrder 和原 billItem 状态。

### 7.1 原路退与逆向结算判定

`shouldReverseSettlement` 当前规则：

1. 原 payOrder 是 `OFFLINE_PAY_SUCCESS`：走逆向结算。
2. 收款方类型是 `TUXI`：走原路退。
3. 非总部收款方：
   - 查收款侧 billItem：`billItemRepository.queryByBizCode(payOrder.recObject, payOrder.payCode)`。
   - billItem 不存在或未生成 `billNo`：走原路退。
   - 对 `COURIER_SITE_DELIVERY_FEE`，如果对应月账单未结算：走原路退。
   - 其他已入账/已结算场景：走逆向结算。

对账单状态的特殊判断：

```text
payOrder.orderType == COURIER_SITE_DELIVERY_FEE
→ 查 dayBill
→ 查 dayBill.monthBillNo 对应的 monthBill
→ monthBill.billStatus != SETTLED 时走原路退
```

## 8. 退款编排器

退款执行由 `SettlementRefundCoordinator` 统一选择轮次形态。

### 8.1 首次处理

如果 reverseOrder 尚不存在：

- 原单存在 `PAYING` 的 originPayOrder：
  - 创建 WAIT_RESULT reverseOrder。
  - `reverseOrder.orderStatusEnum = PAYING`。
  - `reverseOrder.extParams.reverseAction = WAIT_RESULT`。
  - 如果当前轮也存在已落定分组，则仍会处理已落定分组。
- 原单不存在 `PAYING`：
  - 有原路退或逆向结算分组：reverseOrder 初始为 `PAYING`。
  - 只有撤销分组：reverseOrder 初始为 `NO_PAY`。
  - 直接进入 `SettlementRefundResolvedWorkExecutor`。

### 8.2 WAIT_RESULT 续跑

续跑入口是 `NewOrderDomainServiceImpl#continueRefund`，通常由原单支付结果更新链路唤醒。

续跑前置条件：

- 能查到原单对应 reverseOrder。
- reverseOrder 必须显式带有 `extParams.reverseAction=WAIT_RESULT`。

如果原单仍有 `PAYING` payOrder：

- reverseOrder 继续保持 `PAYING`。
- 当前轮已经落定的 payOrder 分组仍会被执行。

如果原单已无 `PAYING` payOrder：

- 没有形成任何退款动作：清理 WAIT_RESULT，上收口为 `NO_REFUND` / `NO_PAY` 等状态。
- 存在退款动作：清理 WAIT_RESULT，进入 resolved 执行器处理。

### 8.3 resolved 执行器

`SettlementRefundResolvedWorkExecutor` 在一个事务内统一完成：

- 保存或更新 reverseOrder。
- 撤销未支付原 payOrder。
- 标记原路退原 payOrder 为 `REFUNDING`。
- 标记逆向结算原 payOrder 为 `REFUNDING` 或线下成功直接 `REFUND_SUCCESS`。
- 保存原路退 reverse payOrder。
- 保存逆向结算 reverse payOrder。
- 保存逆向结算红字 billItem。
- 更新原单退款状态。

事务提交后再发送 MQ：

- 原路退：`GenericTradeMessage.newMessage("GENERIC_REFUND", OriginRefundMessage)`。
- 逆向结算：`GenericTradeMessage.newMessage("GENERIC_REFUND", TransferRefundMessage)`。

这样可以避免事务未提交时，下游先消费退款消息却查不到 reverseOrder/reversePayOrder。

## 9. 退款状态收口

### 9.1 reverseOrder

reverseOrder 使用 `orderStatusEnum` 表达退款执行态：

- 有处理中 reverse payOrder：`PAYING`
- 全部失败：`PAY_FAIL`
- 全部线下成功：`OFFLINE_PAY_SUCCESS`
- 有成功：`PAY_SUCCESS`
- 无 reverse payOrder：`NO_PAY`

`refundStatusEnum` 当前不承担 reverseOrder 聚合职责。

### 9.2 originOrder

originOrder 使用 `refundStatusEnum` 表达原单退款进度：

- 只有撤销分组：通常落到 `NO_REFUND`。
- 存在原路退或异步逆向结算：`REFUNDING`。
- 只有线下逆向结算且已直接完成：`REFUND_SUCCESS`。

### 9.3 originPayOrder

原 payOrder 的 `refundStatusEnum` 表达单条支付腿退款进度：

- 原路退：先置 `REFUNDING`，等待原路退款回调。
- 异步逆向结算：先置 `REFUNDING`，等待转账退款回调。
- 线下逆向结算：直接置 `REFUND_SUCCESS`。
- 未支付撤销：置 `NO_REFUND` 且 payStatus 置 `NO_PAY`。

## 10. 退款后置扩展点

退款执行完成后调用：

```text
RefundOrderCreateFinishEnum.handle(command, orderBizConfig.refundPostHandler)
```

默认处理器：

```text
COMMON_CALLBACK
```

可追加处理器：

| 枚举 | 说明 |
|------|------|
| `COMMON_CALLBACK` | 发送新结算协议通用回执 |
| `PROFIT_SHARING` | 推送分润报表 |

`COMMON_CALLBACK` 在退款链路中优先使用 `executeResult.reversePayOrders` 作为回执判断对象；如果没有 reversePayOrder，则退回使用 `cancelPayOrders`。这意味着纯撤销场景也可以通过通用回执向上游反馈。

`PROFIT_SHARING` 在 `command.isForContinue()` 时直接跳过，避免 WAIT_RESULT 续跑重复推送。

## 11. 新场景接入配置清单

新增一个新结算 `bizType`，至少需要确认以下配置。

### 11.1 order.bizConfig

| 配置 | 必填 | 说明 |
|------|------|------|
| `name` | 建议 | 订单名称，缺省为 `bizType` |
| `splitHandler` | 是 | 推荐 `COMMON` |
| `bizType` 或 `bizTypeMap` | 是 | 交易侧 bizType |
| `refundBizType` | 退款涉及逆向结算时必填 | 转账退款使用的交易 bizType |

## 12. 接入建议

1. 优先使用 `COMMON` 拆单，通过配置表达式完成字段映射。
2. `bizCode` 必须是上游全局唯一业务号；重复会被业务幂等直接 ACK。
3. `objectCode` 必须与后续查原单、退款、payOrder 和 billItem 的分表键保持一致。
4. `amount` 只支持两位小数，且必须大于 0。
5. 如果需要创建 billItem，必须同时补齐 `trade.bizConfig.{tradeBizType}.billType`。
6. 如果需要在线支付，必须确认交易 topic、message key、table key、灰度账号配置都已生效。
7. 如果需要通用回执，建议明确配置 `callbackCondition`、`callbackMqTags` 和必要的 `callbackExtParam_*`。
8. 如果退款可能走逆向结算，必须配置 `refundBizType` 和 `refundBillType`。
9. 如果要求重复退款消息可恢复补发，当前代码还不满足，需要新增补偿或恢复机制。
10. WAIT_RESULT 场景依赖原单支付结果更新后调用 `continueRefund`，联调时必须覆盖“先退款、后支付结果落定”的时序。

## 14. 验证建议

建议新场景至少覆盖：

- 正向消息空值、金额精度、重复 bizCode。
- `COMMON` 拆单后 payOrder 字段完整性。
- `pay=online/offline/success/no` 各策略。
- `SAVE_BILL_ITEM` 开关与 `sendBillMsg` 行为。
- 通用回执单 payOrder、多 payOrder、处理中不回执。
- 退款纯撤销、原路退、逆向结算、混合 payOrder。
- 原单存在 `PAYING` 时的 WAIT_RESULT 首次处理与续跑。
- 退款重复 bizCode 当前会 ACK 丢弃。
- 交易 MQ 发送前后，order/payOrder/billItem 状态是否符合预期。
